# docker-practice: containerised web stack with monitoring, backups and CI, plus Kubernetes basics

## Description

A small three-service web stack that starts with one command, serves over HTTPS, and monitors its own health. The backend itself is deliberately simple (a visit counter), because the point of the project is the infrastructure around it, not the application.

I built it to learn the infrastructure side of a team web project: containers, networking, TLS, healthchecks, monitoring, backups and CI. Before this, my Docker experience was a smaller multi-container setup (Nginx, WordPress and MariaDB) - see [Inception](https://github.com/Mayoyama/Inception).

### What is in the stack

```
browser
   │  http://localhost:8080  ──►  301 redirect to HTTPS
   │  https://localhost:8443
   ▼
┌─────────┐   /          ┌──────────┐            ┌────────────┐
│  nginx  │ ───────────► │ backend  │ ─────────► │ PostgreSQL │
│ (TLS)   │              │ (Flask)  │  db net    │            │
└─────────┘              └──────────┘ (internal) └────────────┘
     │  /grafana/              ▲ /metrics
     ▼                         │ (scraped every 15s)
┌─────────┐   queries    ┌────────────┐
│ Grafana │ ───────────► │ Prometheus │
└─────────┘              └────────────┘
```

- **nginx**: the only service reachable from outside. Terminates HTTPS with a
  self-signed certificate, redirects HTTP to HTTPS, and proxies to the backend
  and Grafana.
- **backend**: Flask app served by gunicorn. Endpoints:
  - `/visits`: reads and increments a counter stored in PostgreSQL
  - `/health`: liveness check (is the app process answering?)
  - `/dbready`: readiness check (can the app reach the database? 503 if not)
  - `/metrics`: Prometheus metrics (`http_requests_total`, labelled by path,
    method and status)
- **PostgreSQL**: stores the counter in a named volume. Only on an internal
  network, with no host port.
- **Prometheus**: scrapes the backend's `/metrics`. Internal only.
- **Grafana**: behind nginx at `/grafana/`, login required. Its datasource,
  dashboard and "Backend Down" alert rule are all loaded from files, so a fresh
  clone comes up with the same setup.

### What each part covers

| Part | What I built |
|---|---|
| Stack | nginx, backend and database in Docker Compose; `make` to start, `make down` / `make clean` to stop and clean up; credentials in a git-ignored `.env` with a committed `.env.example` |
| HTTPS | self-signed certificate generated by the Makefile; HTTP redirected to HTTPS; backend and database have no host ports |
| Health | Docker healthchecks on db, backend and nginx; startup waits until dependencies are healthy; `/dbready` reports a stopped database and recovers when it returns |
| Monitoring | request counter in the backend; Prometheus + Grafana; provisioned dashboard and "Backend Down" alert (fires when `up == 0` for 1 minute) |
| Backup | `make backup` dumps the database with `pg_dump`; `make restore` restores the newest (or a chosen) dump; tested by wiping the volume and restoring |
| CI | GitHub Actions on every push: validate the compose file, build the images, run flake8, mypy, shellcheck and hadolint |
| Kubernetes | Kubernetes manifests for the database and backend in `k8s/` |

### Technical choices

- **Python/Flask, PostgreSQL, nginx**: chosen because they are among the most
  common tools in the industry, so the practice carries over. Flask is
  synchronous and minimal, which keeps the backend out of the way.
- **gunicorn instead of Flask's dev server**: the dev server is not meant for
  production; gunicorn manages worker processes.
- **Liveness vs readiness**: `/health` never checks dependencies, so a database
  outage does not mark the backend itself as broken. `/dbready` does check the
  database. This is the same split Kubernetes uses for its probes.
- **Ports 8080/8443**: rootless Docker cannot bind ports below 1024, so the
  host ports are high and the stack runs the same with or without root. Inside the containers nginx still uses 80/443.
- **Everything from files**: Grafana provisioning, the certificate rule and the
  `.env.example` mean the stack does not depend on anything clicked together
  by hand.

### Problems I ran into

- **Backend started before the database was ready.** Fixed with a `pg_isready`
  healthcheck and `depends_on: condition: service_healthy`. After wiping the
  volume it still happened: during its first-start setup, Postgres runs a
  temporary server that only accepts local connections, so the check passed
  too early. Adding `-h 127.0.0.1` makes the check go over the network like
  the backend does.
- **Restore did not bring the count back.** The backend recreates the table at
  startup, so the restore failed with "already exists". Dumping with
  `--clean --if-exists` adds `DROP TABLE` statements at the start of the dump.
- **Line endings.** The repo is on Windows; `.gitattributes` forces LF so shell
  scripts and configs work inside Linux containers.

## Instructions

### Requirements

- Docker with Docker Compose
- `make` and `openssl`
- Python 3.12 and a venv, only for running the linters locally

### Setup

1. Copy the environment file and fill in the values:
   ```
   cp .env.example .env
   ```
   `GF_SERVER_ROOT_URL` must be `https://localhost:8443/grafana/` and
   `GF_SERVER_SERVE_FROM_SUB_PATH` must be `true`.
2. Start everything (also generates the certificate on the first run):
   ```
   make
   ```

### Usage

| URL | What it shows |
|---|---|
| `https://localhost:8443/visits` | the visit counter (accept the certificate warning once) |
| `https://localhost:8443/health` | liveness |
| `https://localhost:8443/dbready` | readiness |
| `https://localhost:8443/metrics` | Prometheus metrics |
| `https://localhost:8443/grafana/` | Grafana (login from `.env`) |
| `http://localhost:8080/...` | redirects to the HTTPS address |

### Make targets

| Target | What it does |
|---|---|
| `make` / `make build` | generate the certificate if missing, build and start the stack |
| `make up` | start without rebuilding |
| `make down` | stop and remove containers and networks (data is kept) |
| `make clean` | same as `down`, and also delete the volumes (data is lost) |
| `make backup` | dump the database to `backups/pg_dump_<date>_<time>.sql` |
| `make restore` | restore the newest dump |
| `make restore FILE=backups/<file>.sql` | restore a specific dump |
| `make lint` | flake8 and mypy (run inside the venv) |
| `make fclean` | remove Python cache files |

### Testing the backup

1. Open `/visits` a few times, then `make backup`.
2. `make clean`, then `make`. `/visits` starts again from 1.
3. `make restore`. `/visits` continues from the backed-up count.

### Testing health and recovery

- `docker compose stop db`: `/dbready` returns 503, `/health` still returns 200.
- `docker compose start db`: `/dbready` returns 200 again, no backend restart needed.
- `docker compose stop backend`: the "Backend Down" alert in Grafana goes to
  Firing after about a minute and a half.

### Kubernetes (extra)

`k8s/` holds manifests for the database and backend only: a Secret and a
PersistentVolumeClaim for the database, and a Deployment and a Service for each.

1. Copy `k8s/docker-practice-db-secret.yml.example` to
   `k8s/docker-practice-db-secret.yml` (git-ignored) and fill in the values.
2. Build the backend image with `docker compose build`. The Deployment uses
   `imagePullPolicy: Never`, so the image must be available inside the
   cluster (with a kind cluster it has to be loaded into the node first).
3. `kubectl apply -f k8s/`
4. `kubectl port-forward service/backend 5000:5000`, then open
   `http://localhost:5000/visits`.
